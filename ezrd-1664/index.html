EZRD-1664 · UAT Verification Report

Stop addresses intermittently ungeocoded

On the Routes tab, assigning students intermittently flipped correctly-geocoded stops to a red "ungeocoded" warning and hid them from the stop list; a refresh restored them. This report covers how we confirmed the fix is live on UAT, how we verified it in the testqa tenant, the result, and one secondary observation worth a decision before it clears hardening.

Verdict

The reported bug is fixed on UAT

Confirmed fixed

With the active session deliberately different from a route's own session — the exact condition that caused the bug — every stop that loads stays fully geocoded. No red "ungeocoded" icons, no refresh needed.

Open question

Under the same mismatch, a private stop referenced by the route disappears from the stop list (it's present under the matching session). Fixed for shared stops; the private-stop path may still be scoped to the active session. One decision needed — see below.

The defect & the fix

Root cause: stops loaded under the wrong session

The Routes tab filters by date, so a route can be viewed while the top session picker is on a different school session. When loading a route's stops, the server looked up each stop's address under the selected session instead of the route's own session. When the two didn't match, the per-session address row wasn't found and the stop rendered as ungeocoded — until a refresh reset things.

The fix — PR #520 (EZRD-1664)

The route-expand path now hydrates stops and their addresses under the route's own (sandboxId, semesterId), not the request/session context. A session mismatch can no longer blank a stop's address. Confirmed display-only — no stop data was ever lost.

Pre-flight — is it actually on UAT?

We verified the fix is in the deployed UAT build first

"Hardening in UAT" doesn't always mean the code is live, so before testing we checked the running UAT image against the fix's merge commit. First pass looked like it wasn't deployed — that turned out to be a stale local gitops checkout. Against the current UAT image, the fix is included.

How we verified

A deterministic session mismatch on testqa

The original bug is intermittent, so instead of chasing it we recreated its precondition on purpose: view a route while a different session is selected, and confirm every stop stays geocoded. Fixture: the testqa route "Activity Bus – Alternative Route A Test", which belongs to the 2026 ~ 2027 session and runs into the summer, so it can be viewed under Summer 2026 too.

1

Baseline (matching session). Session picker on 2026~2027, opened the route, read every stop. All 16 stops geocoded, 0 ungeocoded.

2

Forced the mismatch. Switched the session picker to Summer 2026 while the route's own session stayed 2026~2027 — the exact condition that used to blank stop addresses.

3

Re-read the route under the mismatch and compared stop-by-stop against the baseline.

Method note

The v3 Routes UI renders through an encrypted channel, so we read verification data directly from the live application state (the decrypted objects the UI itself renders) rather than from screenshots — giving an exact per-stop geocoded status for the route under each session.

Pre-fix, the mismatched-session case is exactly what flipped stops to the red ungeocoded warning. On the current UAT build every stop that loads resolves under the route's own session and stays geocoded — the reported symptom is gone.

⚠
Secondary finding — private stop disappears under the mismatch

Under the mismatched session the route references 16 stops but only 15 hydrate — the missing one is a private stop, which is present under the matching session. So the reported red-icon symptom is fixed for shared stops, but a private stop still disappears from the route's stop list under a session mismatch, which matches the ticket's "stops disappear from the list" wording. It looks like the fix's route-session scoping covers shared stops while the private-stop fetch path may still key off the active session.

Decision needed: confirm whether private-stop session scoping is intentional or a missed case, before this fully clears hardening. It's a separate observation and does not affect the primary pass/fail above.
