What this ticket is about

The v3 student grid asks the API for one page of students — POST /api/v3/students/page with { page: 1, pageSize: 50 }. Sometimes it returns more rows than it asked for (e.g. 51 for a page size of 50). The extra rows are the same student twice — identical id, differing only by primaryAddressId. The grid shows a duplicate and the visible row count disagrees with the header total (totalCount, computed from the distinct id list, stays correct).

The cause is a data-quality problem: a student can end up with more than one address row flagged recordType=1, isPrimary=1. Pagination is applied to the distinct student-id list first, then each id is hydrated; the primary-address join assumed one primary per student (1:1) but was actually 1-to-many, so each extra primary fanned the student into an additional row after the page had been sized.

Read side — already fixed

PR #252 replaced the plain equality join with a correlated MIN(id) subquery, so the list picks exactly one deterministic primary per student and never over-delivers, regardless of data quality. Merged to main; uat/prd await operator promotion.

Write side — this PR

Nothing stopped the app from creating a second primary. A concurrent edit in another tab, or a double-submit, appended another isPrimary=1 row. The read-side fix hides the symptom; this guard removes the source.

Write-path root cause (verified)

createAddress (apps/ezrouting/app/address/address.js) has a "delete existing rows first" guard, but it fires only for school/stop records (recordType 2/4):

// student (recordType=1) skips this entirely
if (addr.recordType == 2 || addr.recordType == 4)
    await db(context).delete('DELETE FROM address WHERE ... recordId=?', ...);
var recid = await db(context).insert('INSERT INTO address SET ?', addr); // inserts as-is

So for a student, createAddress never demotes an existing primary and never dedupes — it just appends. It is reached from two interactive entry points: _saveStudentAddress (the student save) and the generic address-create endpoint. A durable prevention already exists elsewhere and is what we mirror: the change-request approve path demotes existing primaries (UPDATE address SET isPrimary=0 WHERE recordType=1 AND recordId=?) before inserting.

Implementation plan

Approach

Add the guard inside createAddress rather than in a caller: it is the single choke point covering both interactive callers, and it sits right beside the existing school/stop delete guard. Before the insert, for a student (recordType===1) whose new row is primary, demote any existing primary for that student in the same scope — mirroring the change-request approve path.

if (addr.recordType === 1 && addr.isPrimary)
    await db(context).update(
        'UPDATE address SET isPrimary=0 WHERE recordType=1 AND recordId=? AND sandboxId=? AND semesterId=?',
        [addr.recordId, addr.sandboxId, addr.semesterId]);

Scoped to (recordId, sandboxId, semesterId) — the exact scope the new row lands in (both 0 for students) — which is stricter than the approve path's unscoped demote. Net effect: a student always ends up with exactly one isPrimary=1 row, so the list can never fan out.

Deliberately minimal

Demote rather than also dedupe identical rows. Demotion alone kills the fan-out (the read side joins on isPrimary=1); a leftover non-primary row is harmless. Full row-dedup via sameAddress is noted as a possible follow-up, not done here (avoids masking legitimately distinct addresses).

Verify the fix

Why the test uses two tabs

The address editor's Primary control is radio-like — checking a new Primary auto-unchecks the others — so you can't get two primaries by toggling within one form. The condition arises from state one form can't see: a second tab or another user whose view predates your change. That's the path worth testing, so the steps below drive the student from two tabs and confirm the fix keeps a single primary.

1 · Set up

  1. Pick a student that already has one primary address — call it P1.
  2. Open that student in two browser tabs (Tab A and Tab B). Both show P1 as the only primary.

2 · Drive the two-tab edit

  1. Tab A: Addresses → Add address → enter a new address P2, check Primary → Save. Tab A now shows P2 as the primary and P1 demoted.
  2. Tab B (still stale — shows only P1): change any field, or just press Save. This is the save that used to re-introduce a second primary.

3 · Confirm in the UI

  1. Reopen the student (fresh) and expand Addresses. Expected: exactly one address shows Primary checked (the newest, P2); P1 is present but not primary.
  2. Go to the Students list. Expected: the student appears once — no duplicate row — and the visible row count matches the header total (a page of 50 shows 50 distinct students, not 51).

Both checks are visible entirely in the app — the address editor shows a single Primary, and the paginated list stops over-delivering.

4 · Teardown

Remove the test address P2 (and any test student) created for the run.
