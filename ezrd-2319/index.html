Route-list stop-cache fix

After EZRD-2111 removed the Redis fan-out, the route list's residual cost was a heavy MySQL view scan that re-ran on every request. This change caches it. Below is what the fix does, and a step-by-step account of how it was tested on UAT.

Verified on uat.pathwiserouting.com · tenant testqa · build 477ef62 · 2026-07-23 · EZRD-2319 ↗

Background

The residual bottleneck

EZRD-2111 already cut the route list's per-request Redis traffic from ~2,757 commands down to ~30. With Redis no longer the bottleneck, the remaining cost moved to MySQL.

A single GET /api/routes (the route-list tab) issued dozens of queries, dominated by one scan over the vwAllStops view. The reason it re-ran every time: the route-list path asks for the "stops used in routes" list. The full-district stop list was already cached in Redis — but the route-only variant skipped the cache entirely, so it re-ran the view plus a tenant-wide subquery on each request. Under the concurrent regression load this tailed toward ~18s and tripped the EZRD-2111 latency guard.

The query that re-ran on the hot path
SELECT * FROM vwAllStops
WHERE sandboxId = ? AND semesterId = ?
  AND id IN (SELECT stopId FROM tripstop JOIN trip JOIN route …)

vwAllStops is a 3-table view (~32 columns). This ran it, plus the IN (subquery), for the whole route set on every poll.

The fix

Cache the route-only stop list too

The route-only variant already had its own distinct cache key — it just wasn't being written to or read from. The fix caches it like the full-district list, so the hot route-list read no longer re-runs the view scan.

The one subtlety: a route's stop membership changes when trip data changes (not only when the stop's own tables change), and each cached row carries the resolved school name. So the route-only list is invalidated on a broader set of tables than the full list — otherwise it could serve a stale route membership or school name:

Full-district list · unchanged
stop stopextra address
Route-only list · now cached + broadened
stop stopextra address + tripstop trip route school
✓

Result shape is unchanged, so every consumer of the stop list is unaffected. The change is surgical — one function in app/stop/stop.js plus a unit test covering the cross-request cache hit, route-table invalidation, the staleness bust, and full-list no-regression. Shipped as PR #537 (2491dc11).

Performance

Why we're confident the scan is gone

The vwAllStops scan is a literal, searchable DB span in APM, so its presence per request is directly observable.

≈20
scans in one route-list request — pre-fix build (still on production)
≈0
on a warm route-list read — post-fix (UAT); reruns only when route data changes
1.47s
heaviest single scan, pre-fix — mid-size tenant under load (per ticket, dev-eks)

On production — still running the pre-fix build — a single route-list request fanned out ~20 of these scans in under half a second: the uncached behavior. On UAT (fixed build) the scan appears only when route data actually changes, then the list is served from Redis. In the controlled reload after my edit, the re-scan showed up exactly when the cache was invalidated, then went quiet — consistent with the cache being active. Note the per-query cost is small in steady state; the 1.47s figure was a mid-size tenant under concurrent load. The fix's win is eliminating the scan from the hot poll path, not making one query faster.

⚠
Scope & caveats — what this verification does and doesn't claim
  • •Magnitude not reproduced on UAT. testqa is a single small route, so the headline 1.47s figure can't show there — it lives in the ticket's dev-eks trace. What was shown is that the scan is gone from the hot path.
  • •Not yet in production. Prod still runs the pre-fix build and still does the scan — the latency win lands when this ships to prod.
  • •Column-narrow / base-table JOIN rewrite deferred. The ticket's sharpened alternative (drop the view, select only the needed columns) was intentionally set aside in favor of caching — smaller blast radius. It's still available if the cache-miss path matters at scale.
