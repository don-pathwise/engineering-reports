EZRD-2049 — Lock SSC Change Requests After Submission

Test plan for the change that freezes a Student Support Coordinator's change requests the moment they submit. Once submitted, a request is read-only; a correction becomes a new, independent request — so a transportation operator reviewing a request never sees its data change underneath them.

Jira: EZRD-2049 · Epic EZRD-1820 (2026 B2S) · implements ROUT-77 · PR: ezrd-mono #454 · Tenant: testqa

Background

What changed and why

A Student Support Coordinator (SSC — the "Super Parent" role) submits change requests for the students they support. Previously they could keep editing a request after submitting it, and the save quietly overwrote the same request row — so an operator mid-review saw the data change. This work locks a submitted request and routes any correction into a separate new request.

Before

Reopening a student with a pending request showed the request in an editable form; re-submitting updated the same request in place. The SSC could change a request already under review.

After

A submitted request is read-only. To make changes the SSC clicks “Submit a new request,” which creates a separate request. Both appear independently on the admin side. Regular parents are unchanged.

Setup

Before you start

  • Sign in to the testqa tenant as a Student Support Coordinator (Super Parent, role 4). The SSC landing page is titled “Search and Create Student Change Request” and can search all students.
  • Have a second sign-in available as a tenant admin to check the change-request queue (Settings → Change Requests), and optionally a regular parent account for the regression check.
  • Pick any student to work with (examples below use one student throughout).
Walkthrough

Test steps

Run these in order as the SSC unless noted.

1

Submit a change request

Open a student, change a field (e.g. a contact phone number), and click Submit. Expect a “Change request submitted” confirmation.

2

Reopen the student — verify it is locked

Go back to the home page and open the same student again. Confirm all of:

  • Every section (General Information, Addresses, Contacts, Transportation) shows as plain read-only text — no input boxes, dropdowns, or enabled checkboxes.
  • The top bar has no “Submit” and no “Change Location on Map.”
  • A “Submit a new request” action is present.
  • The submitted request appears under Change Request History with status Pending.
  • No extra banner or tooltip explaining the lock — the read-only state speaks for itself.
3

Submit a correction as a new request

Click “Submit a new request.” The form becomes editable again, populated from the student’s current data (not your pending change). Change a field and click Submit → expect the confirmation. The form should then re-lock on its own (no page reload needed).

4

Confirm two independent requests

Expand Change Request History — both requests appear as separate Pending rows. Then, as a tenant admin, open Settings → Change Requests: both requests for that student are listed as separate rows, each with its own View / Accept / Decline. Neither overwrote the other.

5

Transportation is locked too

Using a student that has a transportation request on a pending change, confirm that while locked the transportation method/session dropdowns, weekday checkboxes, notes, and any “other site” fields are all read-only, the per-row delete icon is hidden, and “Add Transportation” is hidden.

6

Regression — regular parent unaffected

Sign in as a regular parent with a pending request for their child. Confirm the form is still editable and re-submitting updates the same request in place (unchanged behavior).

⚠
Notes & scope
  • Scope is the SSC change-request form for existing students. Regular-parent editing and the new-student registration flow are intentionally unchanged.
  • Locking is based on live state (a pending request exists), so existing requests lock automatically on deploy — no data migration.
  • Sits alongside EZRD-2037 (Processing/Completed statuses); the lock is status-agnostic.
