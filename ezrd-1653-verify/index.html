Verification guide · EZRD-1653

Splitting a trip added stops nobody assigned

Two runs of the same steps. On production you should still see the bug — extra stops on the receiving buses that nobody assigned to them. On UAT, with the fix deployed, the same split should come out clean.

App · Trip Preparation Tenant · testqa Flow · View/Edit Trip → Break Up Two runs · prod, then UAT
Orientation

What you're doing, in plain terms

Trip Preparation is the “today isn't going to plan” tool. When a bus loses its driver, a dispatcher covers its stops using other buses — often by splitting one trip's stops across two other buses. That's the action you're going to perform, and it's what the reporting district was doing when they hit this.

Trip Prep edits apply to one service day and don't change the permanent route plan — which is why moved stops are labelled “Moved from route …” and carry an undo arrow.

The bug

Each receiving bus gained extra stops with no “Moved from” label — typically a school the bus doesn't serve, dragged in because a student's pickup got separated from it. Those stops reached the driver tablets and parent apps, so a bus showed a longer route with times that didn't match.

The fix

Those stops were scratch work from the arrival-time calculation, never meant to be saved. They're now discarded before the split is stored, so the bus keeps only the stops it was actually given.

  1. 1
    Set the service day, then record each destination's baseline

    For both destination trips write down the number of stops and the time window. The stop count is what the pass/fail check is built on, so this step is what makes the rest verifiable — and the easiest to skip.

  2. 2
    Open Test3 on West Elementary

    Hover the route row, then click the ✏️ next to the trip name — the pencil only appears on hover, and on a narrow window it sits past the right edge.

  3. 3
    Click BREAK UP, tick the two destination trips, then CALCULATE

    The plan screen should look correct — every stop assigned to exactly one bus. Nothing is wrong yet, which is worth noting: the problem comes later.

  4. 4
    Click CALCULATE DETAILS — the bug shows here

    Note the row count. Keep going — the count that decides the result is the one in the saved trip at step 6.

  5. 5
    Save it: SAVE → YES, then NO to notifications

    Answer NO to “send notifications to the parents” so no messages go out.

  6. 6
    Reopen each destination trip and count its stops

    This is the step that decides the result — compare the count against the baseline you noted in step 1. Both trip windows should also be visibly longer than they were.

What you'll see — bug present

On the Calculate Details screen (step 4), each receiving bus's list is longer than it should be. The extra rows are stops nobody assigned — most often a school the bus doesn't normally serve, pulled in because a student's pickup was separated from it.

Spotting one by eye: a row with no “Moved from …” label that isn't a stop this bus already served. Both conditions matter — the bus's own stops also appear without a label, and those are fine. On these two destinations the give-away is usually a school.

The reliable test: stops now > baseline stops + stops assigned to it

Count it on both destinations, in the reopened trip after saving. More stops than anyone asked for is the defect. The trip's time window will also be visibly longer than the baseline you noted.

Decide from the saved trip

The Calculate Details screen shows working stops in both environments, so it can't tell them apart. Base your result on the count in the reopened trip after saving — that's what the driver tablets and parent apps actually read, and it's the only thing this fix changes.

Before you start

Three things that will waste your time

Use the destination trips named above, not others

The Break Up list offers trips whose route isn't in the day's route list behind the modal, and picking one crashes on CALCULATE with nothing on screen to explain it. That's a separate known defect. If you do substitute a destination, first check its route name is visible in the list behind the modal. Both trips named above were confirmed present on their stated date.

The edit pencil only exists while the row is hovered

Hover the route row first. On a narrow window it sits past the right edge — widen the window or scroll the table sideways.

An empty route list means the wrong date

Trip Prep is day-scoped, and the two environments need different dates — 07/29/2026 on prod, 05/27/2026 on UAT. An empty list is almost always a date outside the semester holding the data.

Afterwards

What you leave behind

Both tenants had no prior day-changes on these trips, so everything you see afterwards is yours. A saved split affects only the service day you chose and leaves the permanent route plan untouched.

If you repeat a run, start from a different source trip. Re-running a split over trips you've already split adds to the mess rather than resetting it — on the unfixed environment that makes the symptom worse each time, which is exactly what the reporting district experienced.
