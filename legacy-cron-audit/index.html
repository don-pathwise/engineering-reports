Bottom line
TL;DR

Most of the work is making outputs durable — not reading the source#

Four headline observations frame the rest of the page.

  • Only two legacy jobs already keep durable copies of what they produce or consume: export-ezr-data (S3 backup) and import-fuellogs (raw CSV archived to S3). Everything else writes to /tmp/, ships via SFTP, or mutates a DB — and forgets.
  • Three of the “blocked” reports are actually free wins: export-contact-list-reports, export-dismissal-reports, and export-punch-reports all write date-stamped files that persist on disk or SFTP — easy to grab for parity even though the source code isn't migrated yet.
  • All DB-mutating jobs need a snapshot-before-and-after harness, not a file diff. That's eight of the 22 entries. A generic mysqldump → structural diff helper would cover all of them.
  • Two jobs produce nothing comparable: schoolToolPost POSTs to a third-party REST API (no file output, side-effect is on SchoolTool), and gps-service reload is a pm2 control — obsolete on EKS.

By output type

Parity strategy buckets#

Four distinct validation patterns cover the 22 entries. Each maps to a small reusable harness.

Easy

Durable file output — just grab it

Output already persists (disk, S3, or SFTP). One scp away from a parity test.

  • • export-contact-list-reports — daily-stamped on disk
  • • export-dismissal-reports — daily-stamped on disk (inferred)
  • • export-punch-reports — daily-stamped on SFTP
  • • import-fuellogs — raw input archived to S3
  • • export-ezr-data — single rolling backup in S3
  • • summarize-trips — log file on disk (supplementary)
  • • preprocess-clarknv-map — map files on disk
Timed

Transient file output — needs a snapshot window

Output exists only between two cron ticks. Need a snapshot of /tmp/ on aarzhou before the next run overwrites.

  • • export-student-buses — 201 per-tenant files in /tmp/, every 30 min
  • • export-students-stops — /tmp/gloucesterva-*, Sun–Thu nights
  • • compare-contact-list-daily-changes — /tmp/difference-*, daily 17:05

One snapshot harness can cover all three: ssh aarzhou 'tar -czf … /tmp/<pattern>' scheduled to run a few minutes after each tick.

Harder

DB-mutating jobs — snapshot state before & after

No file output to compare. Need mysqldump of the affected tables before and after each run, then structural diff. A generic ~/Desktop/parity-diff-db.sh would cover all of them.

  • • import-drivers
  • • import-staff-attendance
  • • summarize-trips (trip-summary table)
  • • import-photos / import-photos-2 / import-photos-taftca
  • • import-eligibility-programs
  • • sync-eligibility-programs
  • • update-houston-sandboxes
  • • import-leave-requests
Other

Non-comparable — different validation approach

  • • schoolToolPost — capture each axios request body (wrapper or interceptor) on both legacy and migrated; diff the HTTP payloads. Alternative: compare downstream SchoolTool state via its query API.
  • • gps-service reload — obsolete on EKS (drop entirely; replace with livenessProbe + memory limits if the underlying leak is real).
  • • backup-dbs — already migrated as cron-backup-dbs; just verify both waves produce same .sql.gz output for one window during soak.

Failure detection

How will we know if a legacy cron is failing?#

External traffic is on EKS, but these 22 entries keep firing on the PM2/aarzhou box during the soak. We need a way to detect failures without waiting for a customer ticket. For each job: where does the failure signal land today, what side-effect can we verify externally, and what is the silent-failure risk if no one looks.

📬
Unified signal source — already exists

Per the live CRONJOB file: 9 of the 22 entries have no > redirect, which means crond delivers their stdout + stderr to /var/spool/mail/aarzhou (or /var/mail/aarzhou). One ssh aarzhou tail -n 500 /var/spool/mail/aarzhou reveals every silent cron failure since the last rotation. Combine that with three explicit log files (export.log, backup-output.log, preproc-clarknv-map.log) and two internal redirects (summarize-log, import-programs.output), and we already have a near-complete failure log surface on the box.

Zero code changes required

Every recommended monitor in the table above relies on signals that already exist — mail spool, the three explicit log files, the two internal-redirect logs, S3 object mtimes, DB row mtimes, customer SFTP destinations, and PM2/Datadog data we're already collecting. The full failure-detection layer can be deployed via Datadog monitors, CloudWatch alarms, and small ssh-cron polling scripts — without modifying any of the 21 legacy .sh wrappers or the CLIs they invoke. The /dev/null redirects stay where they are; observability comes from the side effects, not from the cron's stdout.
