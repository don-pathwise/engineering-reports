EZRD-1757 — Route-Split Save Outcome Visibility

Splitting one bus route across other buses in Trip Preparation could fail and tell the dispatcher nothing — no error, and in one case not even a success message. This is the tester's guide: what the ticket turned out to actually be, how to see the broken behaviour today, and how to confirm the fix once it ships. Everything here runs on the testqa tenant.

⚠
Read this before you start

The fix is not deployed anywhere yet. Its pull request is stacked behind the EZRD-1653 fix and merges after it. As of this writing both UAT deployments are running builds that predate even the 1653 fix — so right now UAT is a valid place to reproduce the bug, not to verify the fix. Confirm what is actually live before you test anything (see Environment state).

Background

What this ticket actually turned out to be

The ticket was written as a broken sync pipeline between EZDistrict and EZRouting, and asked for retry logic, a propagation SLA, and a district-facing "sync status" indicator. Investigation found no such pipeline exists.

What the ticket assumed

EZDistrict saves a split, then hands it to EZRouting over some queue or API call. That hand-off silently drops the change, so drivers and parents keep seeing stale routing and nobody is told.

How it actually works

Trip Preparation writes rows into a per-district trip-change table. EZRouting reads those same rows the next time a bus tablet asks for its route. No queue, no cron, no hand-off — a shared table, read on demand. It's a pull.

Because of that, "saved" and "synced" are the same event. There's no window in which a change is saved-but-not-synced, so there is no transient hand-off to retry and no asynchronous delay to put an SLA on. Two of the five original acceptance criteria had nothing to attach to, and the proposed status indicator had nothing to indicate — it could only ever have displayed "the write landed" or "it didn't," which is what a success or error message already says.

But the instinct behind the ticket was right: there is a real silent failure. It's on the write side, not in a pipeline. When a save was rejected, or when the Calculate step crashed, the dispatcher was shown nothing at all. That is what got fixed.

What changed

Five changes, and why it isn't just one message

The approved scope was "make the failure visible, and add the audit trail the ticket asked for." That came out as five pieces. Nothing here changes what a successful split does.

Where Before After
Calculate step Certain destination choices made Calculate crash. The button stayed live and nothing appeared — the only record was in the browser's developer console. A red message naming the trip that can't be used. The modal stays on the destination picker so you can choose differently.
Save outcome A rejected save produced no error and no success message. The modal just sat there. An error message with the actual reason. If some buses were already written, an acknowledgement dialog naming which ones.
Readable error text The underlying failures surfaced as raw internal text, or as nothing usable at all. Plain sentences. Includes a reference code matching the server log, so support can trace it.
Save button Stayed clickable during the save. An impatient double-click fired the whole multi-bus write twice. Greys out while the save runs, re-enables afterwards.
Audit trail No record at all that a trip save had been attempted, by whom, or whether it worked. One entry per attempt — success and rejection — readable in EZRouting's existing audit screen.

The audit trail was acceptance criterion #3 on the ticket, not an addition. The readable-text work exists because a message showing raw internal error text isn't an explainer. The acknowledgement dialog is used instead of a brief message for the partial-save case specifically, because that message has to survive being read — a self-dismissing toast can't carry "check each bus before service."

Reproduce the bug

Seeing the broken behaviour

Run this on an environment that does not yet have the fix. Tenant is testqa in Trip Preparation. Case A needs nothing but the app and is fully deterministic — start there. Cases B and C need browser developer tools.

Pick your service day first

Trip Preparation shows routes for one service day at a time, and a day outside a school term that has routes shows an empty list. That looks like a broken page but is correct behaviour. Before anything else: page the date control back until the Routes list is populated, and use that day throughout. Note the date you settled on — you'll want it for the fix run too.

A

Calculate does nothing, silently

No developer tools needed. This is the one a dispatcher would actually hit, and it reproduces every time.

  1. On the Routes screen, note the route names visible for your chosen service day. This list is what matters in step 4.
  2. Find a route whose trip has plenty of stops to redistribute. Hover its trip in the TRIP column and click the pencil icon to open View/Edit Trip.
  3. Click BREAK UP. You now see a longer list of candidate destination trips, with their route names in the left column.
  4. Select a destination whose route is NOT one of the routes you noted in step 1. The candidate list is searched separately and offers routes the Routes screen didn't load — those are the ones that break. Pick two to be safe.
  5. Click CALCULATE.
Bug confirmed when

Nothing happens. No message, no progress, no advance to the next step. The CALCULATE button stays enabled, inviting you to click it again. If you open the browser console you'll find an unhandled error mentioning calculateBreakup — that console entry is the only indication anything went wrong.

B

A rejected save says nothing at all

Needs developer tools to force the rejection. This is the ticket's headline complaint.

  1. Same trip, but this time pick destinations whose routes are on the Routes screen, so Calculate succeeds.
  2. Click CALCULATE, then CALCULATE DETAILS. You should reach the preview step with a SAVE button.
  3. Open developer tools → Network. In the request filter box type api/trip so you can watch the save requests.
  4. Set the throttling dropdown to Offline. (Right-clicking a prior request and choosing "Block request URL" also works.)
  5. Click SAVE, then confirm YES on the prompt.
Bug confirmed when

The modal stays open and no message of any kind appears — not an error, and not the usual green success message either. There is no way to tell from the screen whether anything was saved. Set throttling back to No throttling when you're done.

C

A half-saved split puts one stop on two buses

Optional and fiddly to time by hand. Engineering has already captured this one — treat it as background unless you want to see it yourself.

A split is not one save. It writes each destination bus as a separate request and then the source bus last — and that final write is the one that records that the stops left. So if a write fails partway, the destination buses have already claimed stops that the original bus still lists as its own.

  1. Set up as in case B with two destination buses, and reach the SAVE step.
  2. In Network, let the first POST api/trip complete, then immediately switch throttling to Offline so the later ones fail.
  3. Reopen the original trip and the destination you saw succeed, and compare their stop lists.
Bug confirmed when

The same stops appear on both the original bus and the destination bus, and nothing on screen ever warned you. In engineering's capture of this, ten stops were live on two buses simultaneously with no message shown.

Verify the fix

Confirming it once the fix is live

Same tenant, same service day, same trips. Re-run each case and look for a message where there previously was none. The wording below is what the code produces — the trip and route names will be whichever ones you picked.

Case A passes when

Clicking CALCULATE with an unloaded destination route produces a red message along these lines: 

"AM-HS-ATH-62" cannot be used as a destination: its
route is not loaded for this service day. Select a
different trip.

The modal must stay on the destination picker, and CALCULATE must be usable again afterwards. Check the browser console too — the unhandled error that used to appear on this click should be gone.

Case B passes when

A save that is rejected before anything is written produces a red message that begins: 

Nothing was saved. The server could not be reached.
Check your connection and try again.

Wording after "Nothing was saved." varies with the cause — a server that answers with a rejection gives that rejection's reason plus a reference code instead. What must not appear anywhere is [object Object], raw internal error text, or a claim the server was unreachable when it plainly answered. Also watch the SAVE button grey out while the save runs.

Case C passes when

A partly-completed split raises a dialog you have to acknowledge with OK, naming what did save: 

This break-up was only partly saved.

Saved: to the blue place.
Not saved: Trip stops are different on 05/14/2026
(reference 9f4c1a77-…)

The stops that moved may currently show on both the
original bus and the new one. Reopen this trip and
check each bus before service.

The point of this one is that the message is true: the stop really is on two buses at that moment, and the dispatcher is told to go check. The fix reports the state — it does not prevent it. Preventing it is tracked separately.

Audit trail passes when

This one needs no developer tools and is the easiest independent check. Perform any ordinary trip save (a break-up, a stop move, or a stop removal), then open EZRouting → Settings → audit history for the same district and search for [EZD]. You should find a fresh entry like: 

[EZD] Saved to the blue place on 2026-05-13:
10 stop(s) moved in (11 stop(s) stored)

A save the server rejected is also recorded, with — REJECTED and a code appended. Before this fix there were no entries for trip saves at all, so any such entry is itself the pass signal.

Traps

Things that will waste your time

Each of these cost real time during the work. None of them is a bug in the fix.

An empty Routes list is usually the wrong service day

Routes exist only within a school term that has them. A date outside one shows nothing and looks broken. Page the date back until routes appear.

Two UAT hostnames exist and they run different builds

Trip Preparation is reachable at two different UAT hostnames whose deployed versions diverge. Confirm the one the tester is actually on, and check its version, rather than assuming both moved together.

A break-up writes real data for that service day

Saving a split changes what drivers would see for that day. Don't leave a test split in place — reopen the affected trips and use the per-stop undo in View/Edit Trip, or pick a service day nobody is relying on.

Repeated stop names are not necessarily a failure

A physical stop can legitimately be served twice on one route. What matters is whether each row is explainable — a "Moved from" label or an original stop. Two identical rows at the same arrival minute with no label is the EZRD-1653 symptom, which is a separate fix.

A console error from the tab component is pre-existing

The break-up modal logs an unrelated error from its tab widget on open. It predates this work and is not what you're looking for. The one that matters names calculateBreakup.

Environment state

Confirm this first

Ground truth for "what's live" is each deployment's own version endpoint — not a release tag or a ticket status. Trip Preparation exposes one at /version on whichever host you're testing.

Check Why it matters
Read /version on the exact host you'll test The two UAT hosts diverge. Testing the wrong one produces a confident wrong answer.
Confirm the EZRD-1653 fix is present This fix merges after it. A build without 1653 definitely doesn't have 1757.
Note the service day you used The bug run and the fix run must use the same day and trips to be comparable.

On the specific names in this guide

Trip and route names quoted above — and the 2026-05-13 service day — come from a local copy of testqa and are shown to make the wording concrete. testqa data drifts, so treat them as examples rather than fixed coordinates. The selection rules are what carry over: a trip with plenty of stops, and destination routes chosen by whether they appear on the Routes screen for your service day. Those rules hold whatever the data looks like when you run it.

Out of scope

Deliberately not fixed here

Reporting a problem clearly is not the same as removing it. These are known, tracked separately, and should not be logged as failures of this fix.

You still can't use those destination buses

Case A now tells you the route isn't loaded. It doesn't load it. The underlying mismatch — the candidate list offering routes the screen didn't load — has its own defect ticket.

A half-saved split is still possible

Case C warns you and tells you where to look. Making the whole split succeed-or-fail as one unit needs a transactional save, which is its own ticket. Note that simply reversing the write order is not a fix — it would trade a stop double-booked on two buses for a stop on no bus at all, which strands a child rather than wasting a stop.

Retry logic and a propagation SLA were dropped

Both assumed a hand-off between systems that doesn't exist. There is no transient failure to retry and no asynchronous delay to measure. Recommended to Product as dropped rather than deferred.

"When will the driver's tablet show this?" is a real but different question

EZRouting picks a change up when a tablet next asks for its route, so a driver already looking at a loaded screen won't see it until their app refetches. That's a genuine delay, but answering it needs device-level telemetry that doesn't exist and can't be answered from EZDistrict. It sits with Product.

The single-stop Move flow has the same gap

Moving individual stops between trips shares the same silent-rejection and partial-write shape as break-up did. This fix covers break-up, because that's the reported incident. The Move flow is a tracked follow-up — so a silent failure there is expected, not a regression.
