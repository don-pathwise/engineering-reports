EZRD-1757 — UAT Test Steps

Splitting a bus route across other buses could fail and tell the dispatcher nothing — no error, and in one case not even a success message. Five checks confirm it now reports. Every route, trip and date below was confirmed live against Prod UAT for tenant testqa, so you can follow them literally.

⚠
Check the build first

Open https://preparation.pathwiserouting.com/version and confirm with the dev team that the commit shown includes EZRD-1757. If it doesn't, everything below will behave the old way — no messages at all — and you'll be recording the bug rather than the fix.

0
Setup

Get to the right screen and day

Do this once. Every check starts here.

  1. Go to https://preparation.pathwiserouting.com/testqa and sign in. You land on Routes / Trips.
  2. The routes list will be empty on today's date. That's correct — today falls in a school term with almost no routes. You need to change the day.
  3. Click the calendar icon just left of the date in the top bar. A month grid opens with ‹ MONTH YEAR › across the top.
  4. Navigate to MAY 2026 — click ‹ to step back a month at a time, or click the month name and the year to pick from dropdowns.
  5. Click day 13. The date should read 05/13/2026.
You're ready when

The list fills with routes including West Elementary, TestQA3, Emergency Transport - West Alternative and several Activity Bus - Alternative Route A entries — 12 routes in total.

Read once

Two things that will otherwise trip you up

There are five environments and two of them look like "UAT"

pathwiserouting.com is the Prod UAT environment and is the one these steps target. It is not the same as UAT (EKS) (ezd-uat.runpathwise.com) or UAT (EC2) (ezd-uat-ec2.runpathwise.com) — those are separate deployments with separate databases, and the routes and trips named below will not all match there. Use the exact hostnames in these steps.

Two routes are named "High Route B" and they behave oppositely

Athletic Transport - High Route B is not available on this day and will produce the error. Emergency Transport - High Route B is available and saves normally. Read the first word, not the last three.

Check 1

A destination you can't use now says so

The one a dispatcher actually hits, and it works every time. Nothing is saved, so there's nothing to undo. Start here.

  1. Find the West Elementary row. It is in the second of the two route tables on the page — scroll down past the first one. Don't bother clicking the COVERED ROUTES tab; it does nothing (see Things that look wrong but aren't).
  2. In the TRIP column, hover over Test3 (6:00 AM ~ 7:27 AM) — a pencil icon appears to the right of the times. It is only there while the mouse is on that row, so move straight across to it. Click it. You may need to scroll the table sideways to see it.
  3. View/Edit Trip opens with 27 stops. Click BREAK UP at the bottom.
  4. A list of 30 candidate destination trips appears. Tick the checkbox for:
    Activity Bus - South Middle  ·  AM-MS-ACT-46
  5. Click CALCULATE.

The dialog stays on the destination list and CALCULATE works again so you can change your pick. Previously this click did nothing whatsoever — no banner, no movement, button still live.

3
Check 3

A save that fails now tells you

The ticket's headline complaint. You make the save fail using the browser's own Network panel — still just clicking, only in developer tools rather than the app.

  1. Set up exactly as check 2 and stop at the preview screen with the SAVE button. Don't click it yet.
  2. Open developer tools (⌥⌘I on Mac, F12 on Windows) and pick the Network tab.
  3. In the throttling dropdown — it reads No throttling, near the top right of that panel — choose Offline.
  4. Now click SAVE, then YES.
Pass — you should see

A dialog you must dismiss with OK:

This break-up did not finish saving.

Stopped at PM-HS-EMRG-88: The server could not be
reached. Check your connection and try again.

The bus it stopped at may or may not have been written,
so a stop that moved can currently show on two buses.
Reopen this trip and check each bus before service.

The bus named after Stopped at is whichever destination it was writing when the connection dropped, so it may differ from the one above. There is no Confirmed saved line here — nothing had been written yet — and that line appearing is what separates this check from check 4.

The break-up dialog stays open behind it so you can retry. Two things to check specifically, because both were real defects caught in review: the text must not contain [object Object], and it must not claim nothing was saved — the request that failed may still have committed, so the wording has to send you to check rather than reassure you.

Before you continue

Set throttling back to No throttling, or every later check fails too.

4
Check 4

The important one — a stop on two buses

The fiddliest, because you have to act mid-save. Worth it: this failure produces the same customer complaint as EZRD-1653, by a different route.

A split isn't one save. It writes each destination bus separately and the original bus last — and that final write is what records that the stops left. Fail in between and a destination has claimed stops the original still thinks are its own.

  1. Set up as check 2 but pick only one destination — Test. That makes exactly two saves (the destination, then the original), so there is only one moment to catch. Reach the SAVE screen.
  2. In Network, set throttling to Slow 3G. This stretches each save so you have time to act between them.
  3. Type api/trip in the Network filter box so you only see the save calls.
  4. Click SAVE → YES and watch the request list.
  5. The moment the first api/trip request completes, switch throttling to Offline. The second save — the original bus — is the one that must fail.

Why one destination, not two. With two destinations there are three saves, and killing the connection after the first stops it on the second destination — you would then see that trip's name rather than Test3 below, which is still a pass but a more confusing one. One destination puts the failure on the original bus, which is both easier to time and the case that actually strands stops.

Pass — you should see

A dialog you must dismiss with OK — not a banner that fades:

This break-up did not finish saving.

Confirmed saved: Test.
Stopped at Test3: The server could not be reached.
Check your connection and try again.

The bus it stopped at may or may not have been written,
so a stop that moved can currently show on two buses.
Reopen this trip and check each bus before service.

Both lines matter. Confirmed saved must name the bus that did save (Test) — that is the line missing in check 3, and it is the whole point of this check. Stopped at must name the original bus (Test3), because that is the save you killed. A dialog rather than a banner is deliberate — a banner fades after three seconds, which is not long enough for "check each bus before service."

If the timing slips and both saves get through, you will get check 2's green banner instead — no harm done, just undo and try again. If neither gets through you will get check 3's dialog, with no Confirmed saved line.

Now confirm the warning is true

Set throttling back to No throttling, close the dialog, then:

  1. Open TestQA3 → Test via its pencil. The stops it took are listed, each labelled Moved from … Test3.
  2. Now open West Elementary → Test3. Those same stop names are still there, as ordinary stops with no "moved" label.

The same stops, live on two buses at once, and in the old build nothing told anyone.

If you can't land the timing, don't sink time into it — check 3 already proves the reporting works.

5
Check 5

Support can now see the save happened

No developer tools needed — the easiest check on the list. The entry is written by Trip Preparation but read in EZRouting; the two share one audit trail.

  1. Do any save first — check 2 is easiest.
  2. Go to https://uat.pathwiserouting.com/testqa and sign in.
  3. Open Settings → Audit.
  4. Search for [EZD].
Pass — you should see

One fresh entry per bus written, timestamped just now:

[EZD] Saved Test on 2026-05-13: 12 stop(s) moved in
(27 stop(s) stored)

Counts depend on how you split, so don't match them exactly — what matters is that entries exist and name the right trip and date. Before this change there were no entries for trip saves at all, so any entry here is the pass. A save the server rejects also gets one, with — REJECTED and a code appended.

This pairing has now been confirmed end to end: a save made in Trip Preparation on Prod UAT appears in this EZRouting instance's audit trail, so the two do read the same tenant database. If no entry appears, treat it as a real failure.

One known gap, already raised separately: the User column reads System rather than the dispatcher who saved. The entry is still correct — this is not a failure of this check — but support cannot yet tell who made the change.

6
Cleanup

Putting the test data back

Checks 2 and 4 write real changes for 05/13/2026. There's a one-click undo per trip.

  1. Hover the trip's row in the routes list — a ✏ pencil appears next to the trip name. Click it. Do this for Test3, then Test, then AM-ALT-EMRG-52.
  2. In the stop table, look at the far right column of the header row. If the trip has changes there's an ↺ undo icon there — click it to revert the whole trip at once. You may need to scroll the stop table sideways to bring that column into view.
  3. Individual changed stops each have their own ↺ in the last column, if you'd rather undo one at a time.
  4. Undoing from either side reverts both buses — the server clears the "moved to" flag on the original and the "moved from" flag on the destination in one operation, so you don't have to undo each end separately.
Expect undo to fail — this is known

On Prod UAT this undo currently does not work, and it lies about it. It shows a red [object Object] banner and a green "Trip changes undone" banner at the same time, while the server rejects the request and reverts nothing — the "Moved from …" labels stay right where they were. This was reproduced on every attempt, on two different trips and two different service days, so assume you'll hit it.

It is a separate pre-existing defect in the undo screen, not a failure of anything on this page — already raised, don't log it again. What to do:

  • Never take the green banner as proof. Re-read the stop table; if the labels are still there, nothing was undone.
  • Don't try to unpick it by hand — moving stops back manually makes a second, messier change on top of the first.
  • Note which trips and service days you touched and hand the list to the dev team. Leaving them dirty is fine; this is a test tenant.
Back to clean when

Test3 shows all 27 stops again with no "moved" labels and reads 6:00 AM ~ 7:27 AM in the routes list, and the two destination trips show no moved-in stops. A destination that took stops also reverts to its original end time — Test back to 6:06 AM.

If you can't get there, that's expected right now — see the box above. Don't treat a dirty tenant as a failed test; none of the five checks depend on cleanup succeeding.

Not a failure

Things that look wrong but aren't

There are two route tables, and the tabs don't switch

UNCOVERED ROUTES and COVERED ROUTES look like tabs but clicking them does nothing — both tables are drawn one after the other down the page. So the trips you need are split across two lists: Test and AM-ALT-EMRG-52 are in the first table, Test3 is in the second. Just scroll. This is a pre-existing bug in the tab control, unrelated to what you're testing — already known, don't log it.

The destination buses show a red ⚠ and 0 / 1

Test and AM-ALT-EMRG-52 have no driver or vehicle assigned, so they're flagged as uncovered. They are still perfectly valid break-up destinations — "uncovered" is not the same as "not loaded for this service day", which is what check 1 is about.

You still can't use those destination buses

Check 1 now tells you the route isn't available. It doesn't make it available. That's a separate ticket — don't log it against this one.

A half-saved split is still possible

Check 4 warns you and tells you where to look. Making the whole split succeed-or-fail as one unit is separately tracked.

A repeated stop name can be legitimate

A bus can serve the same physical stop twice. What matters is that each row is explainable — a "Moved from" label, or an original stop. Two identical rows at the same arrival minute with no label is the EZRD-1653 symptom, which is its own fix.

Moving a single stop can still fail quietly

This change covers the Break Up flow. The MOVE button in View/Edit Trip has the same gap and is a tracked follow-up, so a silent failure there is expected, not a regression.
