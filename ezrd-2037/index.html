“Processing” and “Completed” statuses for SSC New/Change Requests. Accepting a request that needs a transportation review now moves it to Processing; confirming the “I have reviewed the transportation…” checkbox moves it to Completed. The feature

Status lifecycle

Two new status values. The Accept / Decline buttons and the review checkbox are unchanged — only the resulting status is new.

The rule

What makes a request go to Processing

One test decides it: does accepting this request need a transportation review? (In code, needsTransportationReview().) If yes → Processing. If no → Accepted. This is exactly what the Transportation Review Needed ⚠️ column in the queue already flags.

Always triggers Processing

Transportation requestedParent/SSC asks for transportation (a transportation entry is on the request)
Transportation removalRemoves transportation while the student has an existing route/agenda
Primary address changeThe primary address differs from the current one
Address deletedAn address on the student is removed
School changeThe student’s school changes
Rider-type changeRider type changes (e.g. Rider ↔ Not a Rider)
Accepting builds a routeIf accepting auto-generates bus schedules/agendas, it’s marked review-needed even if nothing above applied

Triggers only if the district turns it on

Enabled per-district under the ⚙️ gear in the queue header → Transportation Review Settings. testqa has none of these enabled, so on your local these behave like “never triggers.”

New studentA brand-new student request — only if newStudent is enabled
WithdrawalA withdrawal request — only if withdrawal is enabled
Transportation attributesTransportation code, half-day, bus session, IEP, SPED, wheelchair, or bus aide changes — each is its own toggle
Flagged custom field (UDF)A user-defined field the district marked as review-relevant

Never triggers — stays Accepted

Basic-info editsName, date of birth, gender, ethnicity, family ID
Contact / parent changesAdding or editing contacts, phones, emails
Non-flagged custom fieldsUDF changes the district hasn’t marked as review-relevant
👁
Shortcut for the tester

In the New/Change Requests queue, the Transportation Review Needed ⚠️ column already flags the same “needs review” condition. A row with ⚠️ will go to Processing; a row without it will go to Accepted. It’s a reliable predictor for testing. (Strictly, the final decision is re-computed at accept time, so it can differ if the student’s data or the district’s review settings changed after the request was created, or if accepting generates a new route — edge cases you won’t hit in normal testqa testing.)

1
Open the queue

Log in and find the requests

  1. Go to https://traveltrackerrouting.transact.com/testqa, sign in with your admin account.
  2. Open New/Change Requests: …/testqa#/settings/changes.
  3. Spot the one row with a ⚠️ in the Transportation Review Needed column — that’s John Adams (the school change). Everything else has no ⚠️.
2
The Processing path

Accept the ⚠️ request → Processing

  1. On the John Adams row, click Accept and confirm.
  2. Open the student: Students → search Adams, John → open his Student Details.
  3. Expand Change Request History at the bottom.
  4. Expected: status reads Processing (blue), and the red “I have reviewed the transportation for this student…” card is showing on the General tab, unchecked.
3
The Completed path

Confirm the review → Completed

  1. On John Adams’ General tab, check “I have reviewed the transportation…” and click Save.
  2. Re-open Change Request History.
  3. Expected: status now reads Completed (purple), and the review card/checkbox is gone (can’t be undone from the UI).
  4. Click View on the row → the detail panel header reads Completed.
4
The control case

Accept a no-⚠️ request → stays Accepted

Accept any request without a ⚠️ (a withdrawal like Marilyne Collier, or a new student). Its Change Request History should read Accepted — proving Processing is scoped to review-needed requests and nothing else changed.
