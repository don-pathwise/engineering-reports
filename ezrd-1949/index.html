EZRD-1949 — Map Regeneration

Honest status feedback + tenant scoping · Testing walkthrough

The admin dashboard's map-regeneration action used to report success no matter what happened — and, it turned out, never told EZRouting which district the request was for, so the regeneration never actually ran. Both are fixed. This walkthrough is how to confirm it by clicking, with no database or configuration changes needed.

Test URL: https://admin.pathwiserouting.com  ·  Apps changed: EZRouting + EZRouting Admin

What changed

Two defects, one click

Both were confirmed in code and reproduced before fixing.

Before
  • A green "request submitted" toast appeared before the request was even sent — always, regardless of outcome.
  • The regeneration was dispatched without waiting for a reply, so failures were swallowed silently.
  • The district was never included in the request, so EZRouting could not identify a tenant — the regeneration did not run at all, and the request simply hung.
  • No failure ever reached the agent, which is why the same button got clicked repeatedly and TechOps was asked to push manually.
After
  • A neutral "processing…" toast first — no claim of success until the system knows.
  • The dashboard waits for EZRouting to accept the job, then reports the real outcome.
  • The district is included, so the regeneration actually runs for the tenant you clicked.
  • A failure now produces a red toast naming the reason, at trigger time and if the rebuild fails later.
⚠
Read before you start
  • Both apps must be deployed. The fix spans EZRouting and EZRouting Admin. Deploying only EZRouting leaves the behaviour broken — the tenant-scoping half lives in the Admin app.
  • Confirm what is actually live. Check each app's own /version rather than trusting a release tag.
  • Keep the browser tab open for the whole test. The completion message arrives over a live connection once the rebuild finishes — under a minute for a small district like testqa, roughly 20 minutes for a normal one — and is not stored anywhere. Reloading or navigating away means you will miss it — that is a known limitation, not a failure.
  • Pick a district you are allowed to regenerate. This triggers a real map rebuild for that district.
Recommended district — use testqa

Fox Point Joint No. 2 School District, WI (testqa)

Verified ready on admin.pathwiserouting.com. It is a non-production district with a very small map area, which makes it both safe and fast to regenerate.

Checked State Why it matters
Uses the 2nd Gen routing engine Yes Required — the action only applies to 2nd Gen districts.
Map area (bounding box) Valid Roughly 6.5 × 9.5 km near Milwaukee. An invalid area is the main thing that makes a rebuild fail.
Existing map files present Yes So the menu item will read "Download lastest map and reset…" rather than "Initialize…".
A rebuild already running? No Nothing in flight, so your click is the one being measured.
Map service reachable Yes Confirmed live — the district settings page itself round-trips to the map service to report those file flags.
Expected timing for testqa

Because the map area is small, this district rebuilds far faster than the ~20 minutes quoted for a normal district. Comparable rebuilds complete each map profile in 10–35 seconds, so expect the final completion message usually within a minute, and well under three. If nothing arrives after about five minutes with the tab still open, treat that as a finding and see "Unexpected results" below.

Note: the menu item always forces a full rebuild, even though this district already has map files — so a genuine rebuild does happen, it is not skipped.

The test

Trigger a regeneration and watch three messages

One click, then wait. No setup, no data changes.

1

Open the admin dashboard

Go to https://admin.pathwiserouting.com and sign in.

2

Open Clients and select a district

Choose the district you intend to regenerate. Note its name — you will need it to confirm the right tenant was used.

3

Open the Actions menu and trigger the regeneration

Click "Download lastest map and reset 2nd Gen Routing Engine". If the district has no 2nd-gen map yet, the same item instead reads "Initialize 2nd Gen Routing Engine" — either label is the correct button; they run the same action.

4

Check the first two messages immediately

These appear within a second or two of each other. See the expected results below.

5

Leave the tab open and wait for the completion message

For the recommended testqa district, expect this within a minute (see the timing note above). For a normal district expect roughly 20 minutes, and longer for very large ones. This third message is the one that proves the regeneration genuinely finished.

Expected results — this is a pass

Three messages, in this order

2nd gen road network re-generation requested — processing… 2nd gen road network re-generation started 2nd gen road network of "<your district>" initialized successfully
✓ When Colour What it proves
Immediately Grey The dashboard no longer claims success up front. A green message here instead is a fail.
~1–2 s later Green EZRouting genuinely accepted the job. This green now means something — it only appears after a real acknowledgement.
~20 min later Green The rebuild completed and reached the routing engine. It names the district — which also confirms the tenant-scoping fix, since the old behaviour produced no completion message at all.

Optional extra confirmation: once the completion message arrives, the corrected road should be usable for routing on that district's site.

Unexpected results — what to report

A red message is not necessarily this ticket failing

Surfacing failures is the point of this change. What matters is which failure you see.

What you see Meaning What to do
Red: "Road network re-generation could not be started: …" Working The fix is doing its job — the trigger genuinely failed and now says why. Report the quoted reason; it points at an environment or preprocessor problem, not at this ticket.
Red: "…of "district" failed to regenerate: …" Working The job was accepted but the rebuild failed afterwards. Previously this was complete silence. Report the reason.
Green appears instantly, with no grey message first Fail You are on the old build. Re-check the deployed version of the Admin app.
The click appears to do nothing at all, or hangs Fail Report it — the endpoint is now supposed to always answer.
First two messages fine, but no completion message after a generous wait Separate ticket First rule out having reloaded or navigated away. If the tab stayed open, this is real signal for EZRD-2498 (regenerated maps not reaching the routing engine) — report it there, not here.

Note: the dashboard also contains an older orange "already been initialized within 12 hours" variant. We could not find anything that currently sends it, so it is not expected — mention it if you do see it.

Not testable here — and how it was covered instead

The two red-message paths

Neither red message can be produced by clicking in a healthy environment.

  • • The immediate "could not be started" message appears only when the trigger itself fails — an unreachable or misconfigured map preprocessor. On Prod UAT the preprocessor is configured and reachable (confirmed live), so a click correctly succeeds.
  • • The later "failed to regenerate" message appears only when a rebuild that started successfully then breaks. The usual cause is a district whose configured map area is missing or nonsensical.
No district on Prod UAT will produce an error

All 657 districts on Prod UAT were checked read-only for the conditions that make a rebuild fail. None matched: every district has a valid, sensibly-shaped map area inside the North America map data — including the qatest district, which the source code comments name as a stub expected to have a blank one. There is therefore no district a tester can pick to see the red message; it would require deliberately breaking a district's configuration or the environment itself. If you want to see the red message anyway, the optional appendix below shows a safe way to simulate it from the browser.

Rather than ask anyone to break UAT, those branches were verified two other ways before this shipped:

  • 1. Verified in a local environment by manipulating configuration. With the map preprocessor address deliberately left empty, and separately pointed at an address nothing is listening on, the action was triggered from the real dashboard. Both produced the grey "processing…" message followed by the red "could not be started" message quoting the underlying reason — and no false success. The previous behaviour in the identical setup was a single green "request submitted" and silence.
  • 2. Automated tests. Both failure shapes — a rejected dispatch and a failing map-existence check — are pinned by unit tests that fail without the fix, including one asserting the endpoint always answers rather than hanging.

So the practical split is: confirm the success path in UAT by clicking (this document), and treat the failure paths as already covered — optionally simulating them in the browser via the appendix below. If you do happen to see a red message in UAT for real, that is the same verified path firing — capture the quoted reason.

Optional appendix — not required for sign-off

Seeing the red messages without breaking anything

Since no district on this environment can produce a genuine failure, the two red messages can instead be simulated from the browser's developer console. This is entirely optional — skip it and the walkthrough above still constitutes a complete test. It is here for anyone who wants to see the failure styling and wording with their own eyes.

Safe to run

Neither recipe changes any data, and neither starts a real regeneration — recipe 2 deliberately intercepts the request before it leaves the browser. Everything is undone by reloading the page. All three snippets below were run and confirmed working in a browser before this document was written.

Step 1 — open the console and locate the app

Sign in to https://admin.pathwiserouting.com, open the Clients page and select a district, then open DevTools (F12, or ⌥⌘I on a Mac) and go to the Console tab. Paste this and press Enter: 

// Locate the running app. Read-only — sends no requests, changes nothing.
const nav  = document.querySelector('nav-bar').au.controller.viewModel;
const app  = nav.constructor._app;
const page = nav.router.currentInstruction.viewPortInstructions.default.component.viewModel;
({ appFound: !!app, socketConnected: !!(app && app.socket && app.socket.connected),
   pageFound: !!page, district: page && page.product && page.product.name })

You should see appFound: true, socketConnected: true, pageFound: true and the district you selected. If any of those are false or the line errors, stop here — the rest will not work, and that is a documentation problem, not a test failure. Note it and move on; nothing about sign-off depends on this appendix.

Recipe 1 — the "failed to regenerate" message

This hands the page the exact notification the server sends when a rebuild dies partway through. Paste it in the same console session, immediately after step 1: 

app.socket.onevent({ data: ['message', {
  name: 'fastRoutingInitFailed',
  data: { client: 'testqa', error: 'simulated: invalid map area for testqa' }
}]});

Expected: a red message reading

2nd gen road network of "testqa" failed to regenerate: simulated: invalid map area for testqa

This is the closest thing to a real failure available here: everything the browser is responsible for runs for real — receiving the notification, deciding it is for you, and rendering it. Only the server's internal hop is stood in for.

Recipe 2 — the "could not be started" message

This makes the next regeneration request come back as a failure without ever reaching the server. Paste it, then trigger the action from the menu exactly as in the walkthrough above: 

// Intercepts the request in the browser — no regeneration is started.
page.api.__origCall = page.api.call.bind(page.api);
page.api.call = async (a, m, url, d, h) =>
  String(url).startsWith('/api/routing/init')
    ? { init: false, error: 'simulated: connect ECONNREFUSED 10.0.0.5:5600' }
    : page.api.__origCall(a, m, url, d, h);

Expected: the neutral message, then a red one — and no green success:

2nd gen road network re-generation requested — processing… Road network re-generation could not be started: simulated: connect ECONNREFUSED 10.0.0.5:5600

Undo it with page.api.call = page.api.__origCall; or simply reload the page. Until you do, that district's regeneration action stays intercepted in your browser tab only.

Bonus — a before/after with no broken environment

Run each recipe once before the fix is deployed and once after, and you get a direct demonstration of the defect:

  • Recipe 1, before:nothing happens at all — the old build has nothing listening for failures. That silence is the bug.
  • Recipe 2, before:a green "request submitted" — the old build announced success before asking.
What this does and does not prove

These recipes prove the browser reports failures correctly. They do not prove the server produces those failures — that half is covered by automated tests plus the local configuration-manipulation run described in the previous section. Together the three form complete coverage; individually none of them does.

Out of scope

What this ticket does not claim to fix

  • EZRD-2498 — regenerated maps not reaching the routing engine. If a regeneration completes but a district still routes on old roads, that belongs there. This ticket makes that situation visible; it does not claim to prevent it.
  • Status does not survive a page reload. Messages are live-only. Confirming an older regeneration after the fact is a known gap, not part of this change.
  • Per-agent attribution. The completion message is per district, not per person — if two agents trigger the same district, both see the same message.
