EZRD-1276 — Post-Save Waterfall Analysis
What reloads after a student save, what's necessary, and what to do

EZRD-1276 · Spike report · Branch: spike/ezrd-1276-student-save-latency

TL;DR

Backend save itself is fast (0.1–0.3s). The 30–40s pain on Clark is the UI tearing down and rebuilding the entire student detail view on success — firing ~20 requests including two unfiltered multi-MB map fetches and a /students/routed call that triggers a hidden SELECT * FROM trip with no WHERE clause. Almost none of these are required by the act of saving.

The single highest-leverage fix is changing _saveStudent() in ui/src/student/details/details.js:283-309 to merge the response into the in-memory student instead of calling getStudent() at line 297.

The pattern behind the table

Three classes of waste, in priority order.

1. Full-page rehydration on a partial-state change

The save handler treats success the same as a fresh route into the page — getStudent() rebuilds everything. Of the ~20 calls, only items 1, 6, 14–17 carry data that the save plausibly invalidated. The other 12 are unconditional context-loads (zones, walking restrictions, settings, properties, stops, equipment, district boundary, notifications, attendance).

2. Backend handlers that fan out far beyond their stated job

The /students/routed call for one student silently loads all routes + all trips + all stops + all schools for the sandbox via attachMoreToAgenda. The SELECT * FROM trip with no WHERE clause at app/agenda/agenda.js:435 is the worst single query — table scan of every trip across every tenant context for an unrelated lookup. The noRideWith path fans into per-address N+1 stop lookups using a LIKE 'name%' scan.

3. Static reference data fetched per-save

Ethnicity codes, tcodes, equipment types, walking restrictions, zones, district boundary, settings — none of these change while the page is open. Move them to app-boot, cache them in memory for the session.

Does the Phoenix UI flag affect this?

No. The Phoenix UI feature flag does not gate any part of the post-save flow on the student details page. The save handler, the post-save reload (getStudent()), the model layer, the HTTP layer, and every one of the ten studentLoaded child-component subscribers contain zero references to isPhoenixUI, isPhoenixStudentPagination, or isPhoenixRouteListV3. The same is true for every backend handler in the waterfall (app/student/, app/agenda/, app/zone/, app/stop/, app/attendance/).

Where the Phoenix flags do branch is in ui/src/student/services/model.provider.js:55-56: 

if (this._me.usePaginatedAPI()) return this._phoenixPaginatedModel;
if (this._me.isPhoenixUI()) return this._phoenixModel;

That switch only chooses between StudentListModel, PhoenixStudentListModel, and PhoenixPaginatedStudentListModel on the student list page. enablePhoenixRouteListV3 does the equivalent for the route list. The details page always uses StudentDetailsModel directly, with no provider indirection. Toggling the Phoenix flag changes the latency of the /students list endpoint (the 309k-row, 106 MB fetch flagged in the spike report) but has no effect on the 30–40s post-save slowdown.

Caveat worth knowing. The redis flag-type-comparison bug at app/shared/redis.js:141 and app/shared/feature-flags.js:128 can silently flip any flag's evaluated state if someone sets it via redis-cli SET ... 1 (a bare number rather than a quoted string). If you ever try to A/B the Phoenix flag against save latency by toggling Redis directly, that bug could mask the answer. The code investigation above bypasses that risk — the post-save path simply has no Phoenix branch to flip.

Recommended sequence (best ROI first)

  1. Stop calling getStudent() after save — return the hydrated student in the PUT response and merge it. Cuts ~15 of the 20 calls in one stroke. (ui/src/student/details/details.js:297 is the trigger; model.details.js:283-354 is the model save method that needs to capture and return the updated record.)
  2. Add WHERE sandboxId=? AND semesterId=? to app/agenda/agenda.js:435 (SELECT * FROM trip). One-line fix, big drop in /students/routed cost.
  3. Batch attachAddressStops in app/student/index.js:936-948 — single name IN (?) query instead of per-address LIKE.
  4. Add semesterId filter to the noridewith query in app/student/student.js:534.
  5. Hoist static reference loads (ethnicity, tcode, equipment, walking restrictions, zones, settings, district boundary) to app boot or a singleton with TTL. Items 2, 3, 4, 5, 10, 11, 12, 13 in the table go away on the save path.
  6. Gate studentLoaded re-fetches on dirty fields — address-related child components only refetch paths/addresses if address fields actually changed.
Steps 1 + 5 alone should take post-save perceived latency from 30–40s to under 1–2s on Clark, without touching any SQL.
