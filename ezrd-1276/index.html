1. TL;DR

The save itself is fast (~0.3s). The 30–40s latency comes from the frontend completely reloading the student detail view after every save — re-fetching 24 MB of zones, stops, paths, and 20+ other requests that haven’t changed.

On dev/local with Clark-sized data, the full post-save reload takes ~5s. On production Clark, network latency to RDS and concurrent load likely inflate this to the reported 30–40s. The noRideWith siblings query alone takes 3s locally.

5. Root Cause

Root Cause Unnecessary full-page reload after save

After PUT /api/student/:id completes, details.js:297 calls this.getStudent() which triggers a complete teardown and rebuild of the student detail view — including 20 MB of map zones, 3.7 MB of stops, path calculations, siblings, attendance, and 20+ other API calls. None of this data changed as a result of the save.

The save transaction itself completes in 0.1–0.3s. The perceived 30–40s latency is entirely the reload waterfall, amplified on production by network latency to RDS and concurrent user load.

6. Detailed Findings

F1 Post-save full reload transfers ~24 MB

The frontend makes 25+ API calls after every save, re-downloading zones (20 MB), stops (3.7 MB), paths, attendance, predators, ethnicity codes, overlays, and more. On dev this takes ~5s; on prod Clark with network overhead, it reaches 30–40s.

ui/src/student/details/details.js:297 → this.getStudent()

F2 noRideWith siblings query: 3s per call

The /:id?noRideWith=1 endpoint takes 2.99s on dev with Clark data — the single slowest request in the waterfall. This fires on both initial load and post-save reload. Likely doing an unbounded scan of 309k students to find siblings.

F3 Zones endpoint returns 20 MB per call

The zones?type=1&date=... endpoint returns all geographic zones for the tenant. This is map display data that has zero relationship to a student save, yet re-fetches on every save.

F4 GET /api/stop/simple returns ALL stops (3.7 MB)

All 36,419 stops are fetched to display stop pins on the map. Also called in the backend during attachMoreToAgenda() in app/agenda/agenda.js:382, which fetches every stop in the sandbox then filters in JavaScript.

F5 Legacy student list returns 106 MB (non-paginated)

GET /api/students returns all 309k students in a single JSON payload (106 MB). The Phoenix pagination flag exists but requires two flags to be enabled: the client-level phoenixClient toggle AND the enablePhoenixStudentPagination feature flag. The feature flag is gated behind Firebase Remote Config → Redis → in-memory cache, with a type-comparison bug (see Bonus).

F6 Backend hydration has N+1 address-to-stop lookups

In app/student/index.js:936, attachAddressStops() loops through each address and calls stopMod.getStopByName() individually. A student with 3 addresses = 3 separate DB queries. Relatively minor with Clark’s max of 3 addresses per student, but a code smell.

app/student/index.js:936–948

F7 attachMoreToAgenda() fetches all stops, schools, routes, trips

The agenda enrichment at app/agenda/agenda.js:382 calls getAllStopsSimple() (all 36k stops), SELECT * FROM vwAllSchools, and loads all routes and trips for the sandbox. This runs during both the save transaction (for compareChanges) and the post-save hydration.

app/agenda/agenda.js:382–482

7. Suggested Remediations

Immediate Impact (addresses the 30–40s directly)

  • S1. Eliminate the full-page reload after save. Instead of calling this.getStudent() (which rebuilds the entire detail view), only re-fetch the student record itself (GET /api/student/:id) and update the in-memory model. Map data (zones, stops, paths) should be preserved — they don’t change on a student field edit. This alone likely reduces save latency from 30–40s to < 1s.
    ui/src/student/details/details.js:297
  • S2. Optimize the noRideWith siblings query. At 3s per call, this is the heaviest single request. Profile the underlying query — likely needs an index on the family/sibling lookup columns, or the result should be cached since siblings don’t change during a save.

Medium-Term (improves overall Clark experience)

  • S3. Cache map data on the frontend. Zones (20 MB) and stops (3.7 MB) should be loaded once per session and invalidated only when actually modified. These are tenant-level resources that change infrequently.
  • S4. Paginate the student list for all large tenants. The 106 MB student list response should never happen. Enable enablePhoenixStudentPagination for Clark in production. Fix the Redis type-comparison bug (see Bonus) so manual flag setting works correctly.
  • S5. Filter attachMoreToAgenda() at the query level. Instead of fetching all 36k stops then filtering in JS, pass the required stop IDs into the query. Same for schools, routes, and trips.

Longer-Term (scalability)

  • S6. Batch the N+1 address-to-stop lookups. Replace the per-address getStopByName() loop with a single WHERE name IN (...) query.
    app/student/index.js:936–948
  • S7. Return updated fields from save response. The PUT currently returns { id, autoAssignStatus }. If it returned the updated student object, the frontend wouldn’t need to re-fetch at all.
  • S8. Make fullAutoAssign always async. For non-Phoenix clients, auto-assign blocks the save response synchronously. Move all auto-assign to BullMQ queues regardless of client config.
    app/geo/features/autoassign.js:182–204

8. Bonus: Feature Flag Type Bug

Bug Feature flag comparison uses strict equality with mismatched types

The redis.get() wrapper at app/shared/redis.js:141 runs JSON.parse() on every value. The feature flag reader at app/shared/feature-flags.js:128 compares with:

flagCache.set(flagName, cached === '1')

If the cron worker or an operator stores a bare 1 (e.g., redis-cli SET rc:flag:name 1), JSON.parse("1") returns the number 1, and 1 === '1' is false. The flag silently evaluates as disabled.

The cron worker presumably stores "1" (JSON-encoded string) which parses correctly, but this is fragile and undocumented. The comparison should be cached == '1' or Boolean(cached).
