EZRD-1653 — Route Split Stops Leak · Test Steps

When a route is split across two or more buses in Trip Preparation, one destination bus ends up showing the other bus's stops (and the whole original route) with wrong timing. This confirms the fix. Test on a dev test tenant (e.g. testqa) after the fix is deployed.

EZRD-1653 · fix in ezrd-mono#509 · reporting tenant per the Jira ticket

What was wrong

A dispatcher split one route across two buses (e.g. Bus 5 → half to Bus 3, half to Bus 6). It looked correct in EZDistrict, but the driver tablets (SD360) and parent apps showed one of the destination buses carrying all of the original route's stops — its own share plus the other bus's share — with incorrect stop times. No error appeared anywhere; a silent failure.

Root cause (confirmed against production data)

This is a write-side data-integrity bug, not a sync/transport failure. The split persisted a destination trip that contained the other destination's stops as unflagged duplicates — its own stops correctly tagged as "moved here," plus the other bus's stops left in as plain, un-tagged copies. Everything downstream then faithfully rendered those extra stops. (The originally-suspected causes — a missing EZD→EZR token, the routing-side new-trip filter, and the tablet render path — were each checked and ruled out against the data.)

Why it was only seen for one client

It is workflow-specific, not tenant-specific — nothing about the reporting district's data triggered it:

  • • The everyday operation is moving stops to one new trip — that path is clean and unaffected.
  • • This bug only appears when splitting one route across two or more buses in a single break-up. That is a much less common operation, so most tenants never hit the path. (It needs a second destination for stops to bleed into.)
  • • It is amplified by repeating the split on the same buses: the destination's stop list is read from accumulating change data, so a later split can start from a base that already contains the other bus's stops. The reporting customer recreated it several times.

Implication: any tenant doing the same multi-destination-split workflow is exposed — worth spot-checking other tenants' split data separately from this code fix.

The fix

In the Trip Prep break-up flow, each destination trip's computed stop list is now filtered to drop any stop the break-up plan assigned to a different destination that has leaked onto this one. Stops legitimately moved to this trip (and the trip's own stops) are always kept, so nothing valid is removed.

⚠ Verification status — read first

The fix was landed on code analysis, not a reproduced run — the affected service could not be exercised in a local sandbox. This test session is the first live verification. Please also confirm the trigger conditions (single split vs. requiring a repeat) and flag if the customer's case actually came from the manual "move stops to a new trip" flow rather than the "Break up trip" tool — that path would need a follow-up.

Setup

  • • Environment: dev, EZDistrict → Trip Preparation, a test tenant (e.g. testqa).
  • • A source route whose trip has several stops (~10+).
  • • At least two other buses to receive the split halves.

1 · Split one route across two buses (main fix)

  1. Trip Preparation → open the source route's trip → Break up trip.
  2. Assign roughly half the stops to Bus A and the other half to Bus B (two destinations in the one break-up). Save.
  3. Open Bus A's resulting trip, then Bus B's, on the driver/SD360 read view (and a parent app if handy).
Expect: each bus shows only its own assigned stops (plus any school/depot anchor), with the correct post-split times. Neither bus shows the other's stops or the full original route.
Pre-fix failure: one destination shows its share plus the other bus's stops (≈ the whole original route) with wrong timing.

2 · Repeat the split on the same buses (accumulation)

  1. Perform a second break-up affecting the same source/destination buses (as the customer did).
  2. Re-check each destination bus's stops.
Expect: still clean — no build-up of the other bus's stops across repeated splits.

3 · Split affects AM and PM (both sessions)

  1. Split both an AM trip and a PM trip across two buses.
  2. Check each destination for both sessions.
Expect: AM and PM each show only the correct per-bus stops and timing.

4 · Move stops to a single new trip (regression)

  1. Use the ordinary "move stops to a new trip" flow — one source, one destination.
Expect: the destination shows only the moved stops — unchanged from before (this path was already correct and must not regress).

5 · Data spot-check (optional, engineering)

In the test tenant's trip-change records for the split date, each destination trip's stops should be only its own moved-in stops (plus anchors). There should be no un-tagged stops that belong to the other destination bus.
