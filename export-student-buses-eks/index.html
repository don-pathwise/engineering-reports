Plan of work

What we'll do, in order

Eight steps from today's EC2-based setup to running entirely on EKS with the same SLA. Everything below this is the spec for these steps.

  1. 1

    Source-control the launcher

    Merge Aaron's PR #19 to bring the 201-line dispatch script and the 5 missing CLI tools into the repo. ✓ In flight

  2. 2

    Translate the launcher into YAML

    One-time mechanical parse: each of the 201 command lines becomes a structured entry in clients.yaml. Per-client flags (--fields, --headers, SFTP target, etc.) become typed config.

  3. 3

    Move SFTP passwords to AWS Secrets Manager

    Push the ~10 plaintext passwords currently inline in the launcher into ezrd/<env>/ezrouting, keyed by client name. The YAML references the secret key, never the value.

  4. 4

    Refactor the CLI tool

    Expose exportStudentBuses(opts) as a pure async function. The existing CLI entrypoint stays in place for backward compatibility during the soak period.

  5. 5

    Add the BullMQ module to ezrouting

    New cron-jobs/export-student-buses/ directory with the scheduler and worker. Two-line registration into the existing cronjob.queues.js. Concurrency 3 in the existing crons-worker pod.

  6. 6

    Notify external-SFTP districts of the source-IP change

    Send a heads-up to the 10 districts whose SFTP servers we push to directly: our source IP changes from ProdWeb_PRIMARY's external IP to the EKS NAT gateway. Some districts allowlist us today and will need to add the new IP; others don't require it. We don't know which is which — defensive notification covers both. Separately: resolve the private-IP routing for stfrancismn (10.32.15.214) — VPN, peering, or a relay from EKS. This is on our side, not the customer's.

  7. 7

    Validate before cutover (method optional)

    Before flipping aarzhou's cron off, we need confidence the new module produces correct output. The simplest approach would be running both systems in parallel and comparing — but that may not be safe here: some customer SFTPs allow only one session per user, and duplicate files arriving 30 seconds apart can confuse customer-side imports. Pick the validation path that fits the risk tolerance:

    • Shadow mode (safest) — EKS writes outputs to a side S3 bucket instead of customer SFTP. Compare hashes against aarzhou's actual files mirrored to the same bucket. No customer-facing duplicates.
    • Per-tenant canary — pick 1-2 cooperative districts, swap their entry from aarzhou to EKS, observe their downstream for a week, then generalize.
    • Schedule offset — aarzhou fires at :00 and :30, EKS at :15 and :45. No duplicates at the destination; real customer infrastructure exercised.
    • Direct cutover (fastest) — rely on dev/uat testing, flip on prd with a rollback plan (uncomment aarzhou's crontab line if anything breaks).
  8. 8

    Cut over and decommission

    Comment out aarzhou's crontab line, delete the legacy .sh from ezrd-async, retire the dispatch script on sftp.ezrouting.com.

⚠
Sizing constraint

Every client must be exported every 30 minutes. No per-client cadence reductions, no event-driven fast paths. The 30-min window is the SLA for all 201 invocations — the new design has to meet it as reliably as the EC2 one does today.

Measured baseline today: 201 invocations × ~6s avg = ~20 min sequential batch, with ~10 min slack inside the 30-min window. Anything we build needs to match or beat that.

Worker
🆕 New

One queue, concurrency 3, in the existing pod

No dedicated worker pod, no fanout machinery, no rate limiter. The module is just another sibling under cron-jobs/ in the existing crons-worker pod, alongside the 9 modules already running there.

BullMQ Worker
const queue = new Queue('export-student-buses', { connection });

// every tick, enqueue all 201 invocations at once
async function fanoutWorker() {
  for (const cfg of clientsConfig) {
    await queue.add('export', cfg, { attempts: 2 });
  }
}

// 3 client exports run at once; the other 198 wait in the queue
new Worker('export-student-buses', exportWorker, {
  connection,
  concurrency: 3,
});

Resource budget

The math works at concurrency 3

Sized against measured behavior, not worst-case projection. The new design is strictly faster than today on every metric while consuming roughly the same resources.

Metric Today (sequential) Proposed (concurrency 3) Headroom
Batch wall-time ~20 min ~7 min 23 min inside the 30-min window
DB connections at peak 1 × 2-3 = 2-3 3 × 2-3 = 6-9 trivial against per-shard limits
Pod memory at peak ~30 MB (one client at a time) ~90 MB (three clients at a time) tiny fraction of pod allotment
Slack for late jobs ~10 min ~23 min 2x today's buffer
Tunable if needed

concurrency: 3 is the only knob to turn. If the batch ever pushes against the window during back-to-school crunch, raise it to 4 or 5. If we ever see DB pressure, drop it to 2. The lever is one config value, not a redesign.

What we considered and rejected

Fanout staggering, DB-shard rate limiter, dedicated exports-worker Deployment, streaming serialization. All useful if the work were 10x larger or coupled to the web app's DB capacity. At the measured ~6s avg job size, they're over-engineering.
