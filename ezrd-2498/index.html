Diagnosis · it was never one bug

EZRD-2498, explained simply

The ticket says: "a support agent regenerates a district's map after a road fix, the regeneration reports success, and the corrected road still never shows up." Nine districts, multiple states, months of retries. This page walks through how the map pipeline actually works, and then shows that the complaint is really three separate problems wearing the same costume — plus a fourth problem that kept all of them invisible.

The complaint

What support keeps experiencing

The same story, over and over. Every step below looks reasonable — which is exactly why this was so confusing.

🗺️
1 · Road fixed on OSM
Someone corrects the road on OpenStreetMap (the public map database our routing is built from) and the edit is approved.
🖱️
2 · Agent clicks "Regenerate"
In the admin dashboard, support triggers a map regeneration for that district.
⏱️
3 · Waits ~20 min
The job runs the full pipeline and reports success.
😕
4 · Nothing changed
Routes still use the old road. Agent retries the next day. And the next.
🛠️
5 · TechOps "backend push"
Eventually someone with server access does something manual — and that fixes it. Every time.

Hold on to step 5. The fact that a manual server-side action always works is the biggest clue in the whole ticket — because it tells us the pipeline can produce the right answer, and the regenerate button just isn't doing whatever the manual action does.

How it's supposed to work

The journey of a road, from OpenStreetMap to a bus route

Production map infrastructure is three servers: one builder that prepares everything, and two replicas that actually answer routing questions from the app. A road edit has to survive this whole relay to reach a district:

🌍
OpenStreetMap
The public map of the world. The district's road fix lives here first.
→
📦
Geofabrik
A service that repackages OSM into one downloadable ~19 GB North-America file (na.osm.pbf), refreshed daily.
→
🗄️
The builder keeps a local copy
The builder downloads that big file sometimes and keeps it on disk. This copy is the master everything else is made from.
→
✂️
Clip + build
"Regenerate" cuts the district's rectangle out of the local master and compiles it into a routing graph (the data structure the engine navigates).
→
🚚
Copy to 2 replicas
The finished graph is copied (with a tool called rsync) to the two servers that answer live routing requests.

The assumption everyone made: "Regenerate" fetches the latest roads. It doesn't. Regenerate starts at the local copy on the builder — it re-cuts the district from whatever master file is already sitting on disk. Think of a photocopier: the master document lives in a drawer, and "regenerate" makes a fresh, crisp photocopy of it. If nobody has replaced the master since the district's road was fixed, you get a beautiful new copy of the old page — and the job honestly reports success, because photocopying worked fine.

Problem A · stale master

The master map rarely gets replaced

Infrastructure code says a timer should re-download the big Geofabrik file every Sunday at 3 AM. I pulled 70 days of server metrics for the builder host (network traffic and disk usage — a 19 GB download is impossible to hide). Result: there is no weekly download. The download-shaped events I can find are roughly monthly and irregular — around Jun 1, Jun 28, and Jul 28–29 — which looks like a human running it by hand, not a schedule. (The handoff had already warned the live schedule on the builder was hand-installed and exists in no repo.)

So if a district's road fix lands between master refreshes, no number of regenerations can ever surface it — the data simply isn't on the server yet. This single fact reproduces the entire support story, including the ending: the "TechOps backend push" that always works is almost certainly manually downloading a fresh master, then regenerating — one support ticket literally documents a "manual download workaround." And support's 20-minute expectation was never achievable by design.

What's still unconfirmed: the exact date-stamp of the master file on the builder. I can't log into the server from this machine (no direct login access to the production hosts from this workstation). One 30-second command by anyone with access settles it — that command is in the handoff. There's also an unexplained ~10 GB of inbound data every day around 10:00 UTC that I can't identify remotely (failed download attempts? backup traffic?) — same host check answers that too.

Problem B · silent delivery skip

The delivery step can silently keep the old graph — and the fix never shipped

Even when the master IS fresh and the builder makes a genuinely new graph, step 5 (copying to the replicas) has a trap. The copy command runs rsync -u, where -u means "skip any file whose copy on the destination looks newer." That sounds safe — except our graph files inherit timestamps from the old map data they were built from, so a brand-new graph can look older than the stale one already on the replica. rsync skips it, reports success, and the replica keeps serving old roads.

Notice what this does to the symptom: requests are spread across both replicas, so the district sees the fix sometimes — the map looks right in the morning and wrong in the afternoon, depending on which server answered. That flaky, per-district, per-server behavior is exactly the "sporadic" pattern in the ticket. And this isn't theoretical: a May 18 incident proved this exact mechanism with file checksums on two real districts — one of which is on this ticket's support list.

The kicker: the fix exists, but production never got it

PR #85 (merged Aug 3) rewrites the delivery step properly: no more -u, and the new graph is staged, verified complete, then swapped in atomically. But "merged" is not "deployed." Production map servers get code through a Jenkins job that ships pre-built bundles from an S3 bucket — and the newest bundle in that bucket was built July 29, five days before the fix merged. I checked the actual code inside that bundle: it still has rsync -au in both delivery paths. So the defect is live in production right now.

✅
GitHub main
Fix merged Aug 3 (PR #85). The code here is correct.
📦
Build bucket
Newest bundle: e1ac742, built Jul 29. The fix is not in it.
🖥️
Production servers
Can only be running pre-fix code — every bundle ever built has the bug.
Problem C · not stale at all

Some of the nine districts never had a stale map

The routing engine (OSRM) doesn't just read the map — it makes choices: it penalizes sharp turns, respects hazard zones, and takes shortcuts through precomputed data structures. Sometimes those choices are wrong even though the road data is perfectly current. From the outside that looks identical to a stale map: "we fixed the road, the bus still won't use it."

🗺️ Stale-data complaint (Problems A/B)

The road is missing or wrong in our copy of the map. A regen with fresh data would fix it.

🧠 Engine-behavior complaint (Problem C)

The road is present and current — but the engine chooses not to use it (e.g. it prices a sharp turn as worse than a huge detour). A regen can never fix this, no matter how fresh the data is.

The tell is in the tickets themselves: one affected district's investigation (EZRD-1607) explicitly notes "map regeneration did not fix the behavior — this rules out a simple stale-data issue," and a second district's (EZRD-2195) records a client-run regen that changed nothing. Both districts are on this ticket's evidence list. This whole class is tracked separately (EZRD-1607, -1787, -1736, -2195), and the biggest one — sharp-turn pricing, EZRD-2114 — was just fixed in PR #86… which, like #85, is also not built or deployed yet.

Problem D · the blindfold

Why nobody could see any of this happening

Each problem above is completely silent: no error, no failed request, a green "success" at every step. The only place the truth exists is in log lines on the map servers themselves — and those servers send zero logs to Datadog (I checked: 7 days, not one line from the builder). Worse, the one monitor built to catch stale graphs is a log-based alert — pointed at servers that ship no logs. It literally cannot fire. Its "OK ✓" status has been meaningless the entire time.

🖥️
Builder + replicas
Everything interesting (download ran? export skipped? copy skipped?) is logged only to local files on these hosts.
✂️
📊
Datadog
Receives host metrics (CPU/disk/network) but no logs from this fleet. The staleness monitor reads logs → sees nothing → reports "OK" forever.

This is why every investigation — including two of mine — kept grabbing one mechanism and declaring it "the" root cause: from the outside, all three problems produce the identical symptom, and the evidence that would separate them was unreachable. It's also why the pending fix-branch commit (5eeb5bc) is still worth something even though it doesn't close the ticket: it makes the pipeline log its decision ("re-exported with new roads" vs "reused cache from <date>") every single time.

Solutions on the table

What we can actually do about each problem

The encouraging part of this diagnosis: none of the four problems needs an invention. Two fixes already exist and are simply stuck at the "merged but never shipped" stage; the rest are a scheduling decision, a UI message, and monitoring plumbing. Each item below is tagged with its status: ✅ exists (code is written — needs build/deploy), 🤔 decision (needs a human to pick an option), or 🔧 build (small new work).

Fixes Problem A · stale master
  • 🤔

    Pick a real refresh cadence and put it in a repo. The strongest cheap option is a daily scheduled download (worst-case staleness drops from "whenever someone remembers" to ~1 day, plus Geofabrik's own ~1-day packaging lag). Weekly merely restores the documented status quo. Either way, the schedule must live in version-controlled infrastructure code — the current hand-installed cron on the builder exists in no repo, which is exactly how it silently stopped matching what everyone believed.

  • 🔧

    Make the button do what TechOps does manually: an operator-triggered "refresh master, then regenerate" action for support. One engineering caution is already known: the download script (map-download.js) kills its own process on failure, so it must run as a separate spawned process — never inside the routing service itself.

  • ✅

    The pending fix-branch commit (5eeb5bc): changes the regen decision from a 24-hour timer to a direct comparison — "is my district's clip older than the master file?" That guarantees a regen run after a master refresh always re-cuts with the new data (the old logic could skip it for a day), and it logs its verdict every time. Worth landing once the host check confirms the ground truth.

  • 🔧

    Tell agents what vintage they're on: surface "road data as of <date>" in the admin dashboard, riding the feedback plumbing EZRD-1949 already built. This is the cheapest expectation fix in the whole ticket — it converts "the regen is broken!" into "your fix will appear after the next refresh," before anyone opens a support ticket.

  • 🔧

    One-time backfill sweep: after the first properly-scheduled fresh master lands, re-export all districts whose clips predate it (there's an existing bulk-regen script for exactly this), so every district starts from the same vintage.

  • ✗

    Considered and set aside: downloading per-state files (~400 MB each) instead of the 19 GB continent. Faster and smaller, but district boundaries cross state lines, so it complicates clipping — not worth it as the primary mechanism.

Fixes Problem B · silent delivery skip
  • ✅

    Build and deploy PR #85 — the fix already exists. It replaces the skip-prone copy with: pull into a staging folder → verify the graph is complete → swap it into place atomically → report a real failure if anything is missing. The only work left is running the Jenkins build and shipping it to the three map servers. Sequencing matters: ship this before fixing Problem A's refresh schedule — the first fresh master in months, pushed through the current skip-prone delivery, would mass-produce exactly the symptom this ticket describes.

  • 🔧

    Small follow-up cleanup: two copies of the same skip-prone flag remain in the EKS chart repo (ezrd-gitops). That environment is a test clone, not customer-facing, so it's low priority — but it should be fixed before the EKS migration ever goes live, as its own small change in that repo.

Fixes Problem C · engine behavior
  • ✅

    Deploy PR #86 (sharp-turn repricing) — merged Aug 4, fixes the biggest engine-behavior complaint (routes taking huge detours rather than making a legal sharp turn). Same situation as #85: done on main, waiting on a build + deploy to the map fleet.

  • 🔧

    Give support a triage rule: if a regeneration ran (with fresh data) and the route still misbehaves, it is not a stale-map problem — file it to the engine-behavior family (EZRD-1607 / -1787 / -1736 / -2195) instead of retrying regens. That one sentence in the support runbook stops the retry-for-days loop and keeps the two problem classes from contaminating each other's tickets again.

Fixes Problem D · the blindfold
  • 🔧

    Ship the map servers' logs to Datadog (already ticketed as EZRD-1830). Every mechanism in this ticket left a log line on the host; none of them left one anywhere we could see. This single change would have shortened months of investigation to an afternoon.

  • 🔧

    Add a staleness signal that can actually fire: have the builder host report the master file's age as a metric, and alert when it exceeds the chosen cadence plus a margin. Unlike the current log-based monitor (pointed at servers that ship no logs), a metric-based alert works today — host metrics are already flowing. Any new monitors must exclude the ci* synthetic load-test tenants or they'll page on every load test.

  • ✅

    Keep the decision-logging from 5eeb5bc: every regen states, in its own log, whether it re-cut with new roads or reused a cached clip and from what date. Combined with log shipping, "did the regen actually pick up new data?" becomes a 10-second Datadog query instead of a multi-week archaeology project.

What settles it

One host check closes the last open question

Everything above is verified except one fact: how old is the master file on the builder right now? Anyone with server access can answer it in one paste (exact commands are in the handoff doc): the date-stamp of na.osm.pbf, the actual schedule (crontab -l), and — for one district from the ticket — the graph file checksums on the builder vs both replicas.

If master is fresh + checksums match everywhere

A and B are acquitted for that district → its complaint was Problem C (engine behavior) → the C ticket family owns it.

If master is old, or a replica's checksum differs from the builder's

Problem A (old master) or B (delivery skip) is confirmed live on a real district — the ticket's "first task" is done with hard evidence.

Recommended order of operations

  1. 1

    Ask the SRE team for the builder-host paste: master file date-stamp, the actual download schedule, and per-district graph checksums on the builder vs both replicas.

  2. 2

    Build + deploy PR #85 (and #86) to the map fleet. Do this before fixing the refresh schedule — the first fresh master in months combined with the delivery-skip bug would mass-produce exactly the symptom this ticket describes.

  3. 3

    Fix the master refresh for real (scheduled download that actually runs, owned in a repo — not a hand-installed cron), and tell agents what data vintage they're on ("road data as of <date>").

  4. 4

    Rescope EZRD-2498 to this A/B/C/D split (its current description names two gaps that are already fixed and describe the wrong failure mode), and turn on log shipping for the map tier so this class of bug can never hide again.
