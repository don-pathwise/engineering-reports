What We Tested and Why

Our system tracks school buses in real time. GPS hardware on the buses and driver tablet apps send location updates constantly. This data flows through several services before a parent opens "Where's The Bus" and sees a dot on a map. We had never stress-tested this pipeline on our dev environment to see how much it can handle, or whether it would break under heavy load. We also needed to confirm that a previous bug (EZRD-813) where bad GPS data caused buses to appear "in the ocean" is still fixed.

We pushed over 15 million GPS records through the system at up to 30 times normal traffic and measured what happened. Here are the headline numbers:

The Good

The core GPS processing engine (Routing) handles 10x normal traffic with zero backlog and survives 30x. The "Where's The Bus" API stays fast even while GPS data is flooding in. Bad coordinates are properly blocked.

Needs Attention

When a bus sends its location, it takes about 10 seconds before a parent can see the updated position on the map. This delay is not caused by Routing — it's caused by a separate service called GPSADV that sits in the middle. This is the biggest issue uncovered by this test.

Can the System Keep Up With Heavy Traffic?

This is the core question. GPS hardware on buses sends location updates to a Redis stream, and a background worker reads from that stream and saves the data to the database. If the worker falls behind, locations get delayed or lost. We gradually turned up the volume from normal levels all the way to 30 times production peak to find where it starts to struggle.

The key metric is "lag" — how many GPS entries are waiting in line to be processed. Zero lag means the system is keeping up perfectly. High lag means it's falling behind.

What This Means

The system comfortably handles 10 times the busiest day we've ever seen without breaking a sweat. There is no immediate need to add more capacity to the GPS processing pipeline. We have a very large safety margin.

How Long Until a Bus's New Position Shows Up on the Map?

This is the most important question for parents: when a bus moves, how quickly does the dot on the map update? What This Means

When a bus moves, it takes about 10 seconds for that new position to show up for parents. Our goal is 3 seconds or less, so this fails the target.

However, the delay is not our code's fault. Our server accepts and forwards the data in under 200 milliseconds. The remaining ~9.5 seconds are spent in GPSADV, a separate GPS processing service that sits between us and the data parents see. GPSADV appears to process data in batches on a timer rather than immediately.

The good news: the delay is rock solid. Over 12 consecutive tests spanning 2 minutes, the delay only varied by 253 milliseconds. It's slow, but it's predictable and it doesn't get worse over time or under load.

Recommended action: Investigate GPSADV's processing interval. If it batches writes every ~10 seconds, reducing that interval could bring the E2E latency within the 3-second target.

Are Bad GPS Coordinates Still Blocked?

Earlier this year, a bug (EZRD-813) caused buses with bad GPS data to appear "in the ocean" on parent maps. The fix added coordinate validation that filters out null, empty, or nonsensical positions. We re-tested this by deliberately sending bad data through both GPS paths to make sure the fix still holds.

What This Means

The "buses in the ocean" bug (EZRD-813) is still fixed. Both GPS paths — hardware devices and driver tablet apps — properly reject bad coordinates before they can reach parents. No bad data leaked through in any of our tests. We also wrote code to log a warning in Datadog whenever bad coordinates are dropped, so the team can monitor if GPS hardware starts sending garbage data. That logging will be verified once the code is deployed.

Test Environment

Important context: Production runs on EC2 with PM2 (20 processes per instance, 4 instances = 80 processes). Dev EKS uses Kubernetes pods with different resource profiles. The numbers in this report give a strong directional signal, but exact production performance may differ. The safety margins we found (10x+ headroom) are large enough that this difference is unlikely to matter.

Summary

The GPS processing pipeline is in good shape. It can handle far more traffic than it currently sees, the parent app stays fast under load, and the "buses in the ocean" bug remains fixed. The one actionable finding is the ~10-second delay between a bus sending its location and that location appearing for parents — caused by the GPSADV service, not by Routing. Addressing that delay would meaningfully improve the parent experience.
